# Architecture — spec 002

## What serves what

```
browser ──► nginx (proxy/nginx.conf, generated by scripts/generate-proxy-conf.sh)
              ├── /                 landing page, or the Sowel UI once `showroom=entered`
              ├── @app, /*          Sowel UI — HTML gets the vignette script (sub_filter)
              ├── /api, /ws         Sowel, deny list and quotas (spec 001), $http_host
              ├── /sw.js            landing/sw.js — the neutral worker
              ├── /showroom-ui/     landing/showroom-ui/ — the vignette's script
              └── /maison/          ${HOUSE_3D_DIST}, read-only, frame-ancestors 'self'
```

The 3D app is a build mounted from outside the stack. The stack never builds it,
so the showroom stays infrastructure: its CI checks the proxy and the scripts, the
3D app's CI checks the app.

## Why inject rather than change the product

The project map's rule: the core stays stock, and anything the demo needs is done
in the plugin, the proxy or the 3D app. A `sub_filter` on HTML from the UI
locations is the smallest change that puts something on every page of the
interface without touching the image. It touches only the UI's HTML: the 3D app,
the landing page and every script are served as they were.

## The vignette and the app talk by anchor

`mini-house.js` sets the frame's `location.hash` to `full` or empty; the app
listens for `hashchange` (house-3d spec 003). Same origin, no reload, no message
protocol to keep in step between two repositories.
